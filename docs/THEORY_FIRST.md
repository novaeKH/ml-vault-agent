# Theory-first: границы продукта и план развития

## Назначение

ML Vault Agent — локальный помощник для изучения и применения теории Machine
Learning. Его основная работа:

1. объяснять концепции и причинные связи;
2. помогать корректно поставить ML-задачу и эксперимент;
3. находить релевантные знания в личном Obsidian vault;
4. тренировать собеседования и алгоритмическое мышление;
5. показывать небольшой код только как иллюстрацию теории.

Агент не является автономным разработчиком, IDE, исполнителем команд или
генератором архитектуры приложения. Такое ограничение уменьшает лишний код в
ответах и оставляет контекст модели для ML-рассуждения.

## Контракт качественного ML-ответа

Перед ответом агент определяет, что требуется: объяснение, выбор метода,
эксперимент, диагностика, метрика, математика или шаблон. Для прикладной задачи он
проверяет только релевантные элементы:

- объект наблюдения, target и момент предсказания;
- решение, которое будет принято по прогнозу;
- train/validation/test и временной порядок;
- leakage, baseline и метрику с учётом цены ошибок;
- ограничения inference, drift и отличие offline-метрики от продуктового эффекта.

Предположения должны быть отделены от фактов. Если недостающая информация не
мешает полезному ответу, агент называет предположения и продолжает. Уточняющий
вопрос нужен только тогда, когда ответ действительно меняет выбор решения.

## Как измерять точность

Качество нельзя оценивать только субъективно. Нужны два небольших приватных
набора вопросов из реального использования:

- **retrieval set**: вопрос и заметка, которая должна попасть в top-3;
- **answer set**: вопрос и чек-лист обязательных фактов, ошибок и допустимых
  предположений.

В репозитории есть CLI для первого набора: `python -m app.eval_retrieval`. После
каждого изменения индекса следует сравнивать Recall@3 и MRR с предыдущим
результатом. Следующий этап — добавить проверку ответов по обязательным фактам без
использования самой тестируемой модели как единственного судьи.

## Уже реализованная оптимизация

- поисковый запрос строится из текущего сообщения; история добавляется только для
  явного короткого follow-up и не включает старые ответы модели;
- слабый retrieval отбрасывается, чтобы нерелевантная заметка не ухудшала ответ;
- контекст диалога ограничивается по приблизительному числу токенов;
- разные режимы имеют собственные лимиты ответа и низкую temperature;
- Markdown во время streaming перерисовывается не чаще одного раза примерно в
  80 мс;
- пользователь может прокрутить ответ вверх: автопрокрутка останавливается и
  появляется кнопка возврата к последней части;
- проверка состояния Ollama выполняется реже, уменьшая фоновые запросы.

## Следующие этапы

1. Собрать 20–30 реальных retrieval-вопросов и зафиксировать базовые метрики.
2. Добавить answer set по основным темам: validation, leakage, метрики,
   feature engineering, классические модели и DL.
3. Профилировать время retrieval, first-token latency и скорость генерации на
   основном ноутбуке и Windows-ПК, после чего оптимизировать подтверждённое узкое
   место.
4. Добавить кэш embeddings запросов и пакетную индексацию только если измерения
   покажут пользу на реальном размере vault.
5. Подготовить PWA/мобильный клиент. До появления аутентификации и TLS сервер
   должен оставаться на `127.0.0.1`: открывать личный vault в локальную сеть
   небезопасно.

## Критерий готовности к GitHub

Новая версия публикуется как единственная ветка `main` после того, как:

- автономные тесты проходят на macOS и Windows;
- интерфейс проверен на desktop и ширине мобильного экрана;
- владелец проверил несколько реальных ML-вопросов на своей модели и vault;
- в коммит не попали `data/`, сам vault, индекс, `.venv` или локальные пути.
